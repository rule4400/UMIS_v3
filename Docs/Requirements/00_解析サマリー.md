# 解析サマリー

## 結論

RINKAN UMISは、記録メディアから写真・動画・RAW・音声を読み込み、撮影日／シーンへ仕分け、規則に従ってリネームしてアーカイブへコピーし、その中から選別素材を作る業務アプリです。機能の幅は広く、初心者が短時間で作業するための導線も相当作り込まれています。

一方、現行v1.1.103は「重いUI」という問題だけではありません。取り込みの正しさを保証する中核モデルに重大な不整合があり、現在のまま業務データの安全性を前提にすることはできません。Swift化ではFlet UIを移植するだけでなく、`MediaAsset ID → Scene ID` の単一割当、検証付きアトミックコピー、永続ジャーナル、安定したボリューム識別、フォーマット許可条件を核から再設計する必要があります。

最優先の発見は、仕分けがファイルのIDではなく配列indexを記録していることです。仕分け後に名前・日付・カテゴリ・サイズ順を変えると配列自体が並び替わりますが、割当indexは更新されません。その結果、利用者が画面で仕分けた素材とは別の素材が、そのシーンへコピーされる可能性があります。割当は [`assign_selected_to_scene()`](legacy-source/rinkan_umis_v1.1.103.py:10876)、並び替えは [`sort_files()`](legacy-source/rinkan_umis_v1.1.103.py:6546)、実コピーの対象解決は [`CopyWorker._run_inner()`](legacy-source/rinkan_umis_v1.1.103.py:1754) に分離されています。

## 解析方法

1. ZIP構造、パストラバーサルの有無、容量、バージョン、ハッシュを確認
2. 最新ソース14,453行、設定、履歴、ビルド、配布補助、変更履歴、引継ぎ文書を静的解析
3. ASTでクラス／関数／状態規模を計測し、コピー、並び替え、メディア、キャッシュ、外部プロセス、更新、初期化のデータフローを追跡
4. 配布済み`.app`のMach-O、CPU、Info.plist、署名、quarantine、Gatekeeper判定を確認
5. `/tmp`の検証用コピーで同梱ランタイム自己診断を実行
6. 隔離したアプリデータ領域でGUIを実際に操作し、取り込み／セレクト／設定／ヘルプ／開発者画面／負荷試験を確認
7. 実メディアには触れず、自動生成素材230件で負荷挙動とプロセス全体RSSを計測
8. Apple公式資料に基づき、Developer ID署名、公証、Hardened Runtime、staple要件を確認
9. FFmpeg公式資料と同梱バイナリのconfigure情報を照合し、ライセンス配布リスクを確認

## P0：リリース前に必ず解消すべき問題

| ID | 問題 | 影響 |
|---|---|---|
| P0-01 | 仕分けが配列index依存で、並び替え後に別ファイルをコピーし得る | シーン取り違え、利用者が確認した結果と出力が不一致 |
| P0-02 | `verify_checksum=True` は設定にあるだけで未使用。検証はサイズ一致のみ | 同サイズ破損、既存同名の誤内容、部分破損を検出不能 |
| P0-03 | 保存先に同名があれば内容比較なしでskipし、失敗0なら全体成功 | 本来の素材が保存されていなくても「完了」、カード初期化を許可 |
| P0-04 | コピー成功後のフォーマット許可が、全原本の内容検証完了を条件にしない | 取り込み漏れのまま原本消去が可能 |
| P0-05 | セレクトのシーン移動は衝突確認なしの`shutil.move`で、複数ファイル非トランザクション | 同名上書き、途中失敗で本体と選別コピーが不整合 |
| P0-06 | updaterが署名・hash・サイズを検証せずURLの内容で現行プログラムを置換・実行 | リモートコード実行、改ざん、frozen app破損 |
| P0-07 | 初期化対象が表示名とmount pathに依存し、`diskutil eraseVolume`にtimeoutも再識別もない | 誤ドライブ消去、UI永久待ち、抜き差し競合 |

## P1：Swift版の品質を左右する問題

- 取り込みは「原本→固定ローカルtemp→保存先」の全量二重コピーで、時間、I/O、空き容量を約2倍要求します。
- ファイル単位のjournal、resume、rollback、`.partial`、fsyncがなく、失敗／キャンセルで部分集合が残ります。
- 1つの`RinkanUMISApp`が348メソッド・216状態属性を抱え、UI、I/O、デバイス、設定、メディア、更新、診断を一括所有しています。
- 3+2+2本のexecutor、専用スレッド、daemon thread、Timer、外部プロセスが混在し、バックグラウンドからFlet controlを直接更新する経路が多数あります。
- 設定保存や一部stat／disk I/OはUIイベント内に残り、Flet control treeの再構築が多く、操作停止と状態破損の温床です。
- 設定ダイアログの「キャンセル」は、開いた後に即時保存された変更を戻しません。
- ヘルプにあるOSファイルDrag & Dropは実装されていません。
- 初回起動フラグはあるもののウォークスルーは自動表示されず、設定から手動再開するだけです。
- 履歴のフィルタ／消去に未接続UIがあり、破損JSONは黙って読み飛ばします。
- 同梱CHANGELOGがPyInstaller specへ含まれず、実アプリの「更新履歴」は「見つかりません」になります。
- Accessibility tree上で多くの操作行がbuttonとして表現されず、ラベル、Value、キーボード操作、VoiceOver対応が不足しています。

## 実測した重さ

隔離環境で、アプリ内負荷試験の30動画＋200 JPEG、計230件を実行しました。11秒で完了しフリーズ判定は出ませんでしたが、アプリ全体の合計RSSは処理中約447MiB、終了後も約410MiBでした。内訳は概ねPythonプロセス約137MiB、Flet view約244MiB、bootloaderその他約30MiB超です。

開発者パネルは同じ時点で約86〜106MiB程度しか表示せず、Flet viewや子プロセスを含まないため、利用者が実際に消費するメモリを大幅に過小評価します。したがって「古いMacやメモリ不足環境で動作困難」という申告は、構造と実測の両面から妥当です。

この試験は高速な内蔵ストレージ・arm64 Mac上の小さい自動生成素材であり、4K動画、実SD、NAS、Intel Macを代表しません。それでも400MiB超が残るため、ネイティブ化の効果余地は大きいと判断します。

## 配布物と署名の現状

現行`.app`は`codesign --verify --deep --strict`には通りますが、署名は`adhoc`でTeamIdentifierがなく、`spctl`はrejectします。Info.plistのBundle IDも`RINKAN UMIS`で、逆DNS形式の製品識別子ではありません。PyInstaller specは `codesign_identity=None`、`entitlements_file=None`、`bundle_identifier=None` です。[`RINKAN UMIS.spec`](legacy-source/RINKAN%20UMIS.spec:59)

旧配布手順はquarantineを解除する`.command`を同梱してGatekeeperを迂回する方式です。[`初回起動.command`](legacy-source/distribution/初回起動.command:36) 新Swift版ではこの方法を廃止します。

Apple Developer Program登録完了を前提に、直接配布の新アプリは次を必須とします。

1. 正式Bundle IDとApple Developer Teamの設定
2. `Developer ID Application`証明書でアプリと全ネストコードを署名
3. Hardened Runtimeを有効化し、必要最小限のentitlementだけを付与
4. secure timestampを付ける
5. DMGを`notarytool`へ送信し、成功ログを保存
6. 公証ticketをDMGへstapleし、オフラインGatekeeper試験を通す

AppleはMac App Store外の直接配布にDeveloper IDを用い、公証準備としてDeveloper ID署名、Hardened Runtime、secure timestamp、全実行コードの有効署名を求めています。[Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/) / [Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

ただし、2026-08-26時点でこのMacのKeychainを `security find-identity -v -p codesigning` で確認した結果は `0 valid identities found` でした。Xcode 26.6、`notarytool 1.1.2`、stapler自体は利用可能です。Developer登録は完了していても、署名に必要な`Developer ID Application`証明書と対応する秘密鍵がこのMacへまだ入っていない状態です。新アプリ完成前に、XcodeまたはDeveloperサイトで証明書を作成／同期し、秘密鍵付きでKeychainへ導入する必要があります。Apple IDのパスワードや秘密鍵をリポジトリへ保存してはいけません。

## Swift再構築の中核方針

- UIは現在の「左：条件／ソース、中：素材、右：シーンまたはインスペクタ、下：主操作」を維持します。
- SwiftUIをウィンドウと設定画面の土台にし、大量素材グリッドはAppKit `NSCollectionView`＋diffable data sourceで仮想化します。
- UI状態は`@MainActor`、スキャン／コピー／hash／メディア生成／デバイス監視はactorへ分離し、UIから直接ファイルI/Oを行いません。
- 素材、シーン、割当、コピー項目は永続UUIDで関連付け、配列indexを識別子にしません。
- コピーは計画、preflight、`.partial`書込、streaming hash、flush/fsync、atomic rename、journal commitの順に行います。
- 「カードを初期化可能」は、非空Required Setの全delivery obligationが今回runで耐久commit済みの場合だけ成立する予備的派生状態にします。別操作の最終検証でsourceと全required destinationを無条件全再読SHA-256し、結果を表示しても自動初期化しません。利用者の明示承認後、source I/O停止、normal unmount、物理media再照合を通過した時だけ一回限りtokenを発行・即消費します。警告を無視して解禁する機能にはしません。
- AVFoundation、AVKit、ImageIO、QuickLookThumbnailing、Core Imageを第一選択にし、optional helperはnative機能または必須性能gapが固定corpusで実証されたoperationだけへ限定します。
- Apple Silicon／Intelを含む古めのMacを対象にするなら`universal2`を前提とし、最低macOSは実利用機一覧を確認して確定します。
- 自動更新は少なくとも初版では廃止し、署名・公証済みDMGの手動更新にします。将来導入する場合は署名付きupdate feedと安全なupdater frameworkを別設計します。

## 追加要件で確定した方針

現行解析後の追加要求により、次をSwift版の正式要件として確定しました。

- Flet、Python、Pillow、rawpy、flet-video、psutilは新アプリへ持ち込まず、Apple native frameworkへ置換する。
- `qlmanage`、`sips`、osascriptを標準処理として起動しない。
- FFmpeg／ffprobeは標準経路から外し、実素材でnative機能または必須性能gapが実証されたoperationだけの署名済み`MediaCompatibilityHelper`へ縮小する。
- `NSCollectionView`のcell reuse／prefetchと、visible-firstのthumbnail pipelineを採用する。
- カード初期化は実装する。ただし非破壊の最終検証でRequired Setのsourceと全required destinationを無条件再読SHA-256し、別の破壊確認、source I/O停止、normal unmount、物理media再照合後にだけauthenticated one-shot tokenを発行・即消費する。
- 既存folderの`Copy and Rename`を初回productionへ追加する。journal付き`In-place Rename`は設計・test targetを完成させ、専用fault／recovery gate通過後の版で有効化する。
- 1台のmaster MacがScene Catalogをpublishし、LAN clientがrevision付きsnapshotを使用する。
- 受領・監査済みのSD管理システムはprotocol-neutral gatewayとdurable outboxへ隔離する。現行browser API、管理者Cookie、管理者passwordをSwiftから直接利用せず、SD側へversioned integration APIとdevice service identityを新設する。
- Card No、Volume Instance、現在の物理media identityを別modelにする。
- LAN／VPSの状態はlocal copy verificationやerase安全条件を弱化できない。

上位要件は[追加要件定義](07_追加要件定義.md)、詳細は[メディア最適化](08_macOSネイティブ_メディア最適化要件.md)、[カード初期化・フォルダリネーム](09_安全なカード初期化_フォルダリネーム要件.md)、[LAN・SD管理連携](10_LANシーン共有_SD管理連携要件.md)に記載しています。実際のSD管理システム受領後の監査結果、必要なserver差分、追加資料は[SD管理システム実装監査](11_SD管理システム実装監査_UMIS連携差分.md)と[判断チェックリスト](12_SD管理連携_不足資料_判断チェックリスト.md)を正本とします。

### SD管理システム受領後の追加判定

SD管理システムのhandoffは整合性を独立確認し、隔離環境でbuild、lint、既存smoke validationを再現できました。現行systemを解析する資料としては十分で、同じsource一式の再送は不要です。

ただし、UMIS向けversioned API、service authentication、stable external ID／revision、server側のdurable idempotency、`ingest_verified`と`ready_for_reuse`の状態分離、ordered migration、current backup／restore rehearsalが未整備です。認証、会場隔離、destructive／restore操作、backup完全性の詳細security findingは、public repositoryではなくaccess-controlledな監査証跡で管理します。これらは本番連携前の修正条件です。

## 現段階の判断

現行コードを段階的にSwiftへ機械移植するより、仕様を固定し、データ安全性のコアを先に作り、その上へ現行UIを再構成する方が安全です。移行順序は「モデル／コピーエンジン→スキャン／メディア→取り込みUI→セレクトUI→設定／履歴→既存folder rename→LAN Scene Catalog／SD gateway境界→verified card erase→署名配布」とします。

現行Flet版は、Swift版が受入試験を通るまで参照実装として読み取り専用で残します。ただし、P0-01〜P0-07があるため、本番素材での比較時はカード初期化機能を使用せず、必ず別バックアップを保持する必要があります。
