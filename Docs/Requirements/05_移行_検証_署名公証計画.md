# 移行・検証・署名公証計画

## 1. 基本方針

現行14,453行を画面単位でSwiftへ逐次翻訳するのではなく、次の順で置き換えます。

1. 現行仕様とfixtureを固定
2. 安定ID、命名、copy journal、hash検証をUIなしで完成
3. legacy project／history migration
4. volume監視、scanner、media pipeline
5. 現行に近い取り込みUI
6. セレクト／archive move
7. 設定、履歴、診断、アクセシビリティ
8. 既存folder rename engine
9. LAN Scene Catalog、SD管理gateway境界
10. 初期化機能を別security gateとして最後に実装
11. universal2、Developer ID、Hardened Runtime、公証、staple

現行Flet版はUIと業務語彙の参照用に残しますが、copy完全性やeraseの正解実装とは見なしません。

## 8. Apple Developer署名の方針

### 8.1 想定する配布方式

現在の要件と、removable media／NAS／外部folderへの広いaccessを考え、ここでは**Mac App Store外の直接配布**を想定します。この場合の正しいidentityは`Developer ID Application`です。`Apple Development`、`Mac Distribution`、ad-hoc署名ではありません。

AppleはMac App Store外のappにDeveloper IDを用い、Developer ID署名と公証ticketによりGatekeeperが配布者と改ざん有無を確認できると説明しています。[Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/)

公証準備では、Developer ID署名、全実行codeの有効署名、Hardened Runtime、secure timestamp等が必要です。[Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

### 8.2 現在のMacの状態

2026-08-26に確認した結果:

```text
security find-identity -v -p codesigning
    0 valid identities found

Xcode 26.6
Build version 17F113

xcrun notarytool --version
    1.1.2 (41)
```

つまり、Apple Developer Program登録は完了していても、このMacのKeychainには署名に使える秘密鍵付きcode signing identityがまだありません。Xcode、notarytool、staplerは利用できます。

Developer ID署名は公開証明書だけではできません。証明書に対応する秘密鍵がKeychainの「自分の証明書」に必要です。

### 8.3 証明書導入

推奨はXcodeで対象Teamへsign inし、Accounts／Manage Certificatesから`Developer ID Application`を作成または同期することです。Developer websiteでCSRを使って作る場合は、証明書を作成した同じMacに秘密鍵が残り、downloadした`.cer`をKeychainへimportします。Apple公式手順では、Mac app用が`Developer ID Application`、installer package用が`Developer ID Installer`です。[Apple certificate creation](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/)

導入後の確認:

```bash
security find-identity -v -p codesigning
```

期待結果:

```text
1) <SHA-1> "Developer ID Application: <組織名> (<TEAM_ID>)"
   1 valid identities found
```

証明書の`.p12`、秘密鍵、Apple ID password、app-specific password、App Store Connect API private keyをGitへ入れません。

### 8.4 Xcode設定

正式値はPhase 0で決めます。

| 設定 | 方針 |
|---|---|
| Product Name | `RINKAN UMIS`を暫定維持 |
| Bundle ID | 逆DNS。例 `jp.<organization>.RinkanUMIS`。実組織値で確定 |
| Team | 登録済みApple Developer Team |
| Version | semantic marketing version |
| Build | 単調増加integer |
| Architectures | Standard Architectures、arm64＋x86_64 |
| Deployment Target | 実利用Mac調査後に固定 |
| Hardened Runtime | ON |
| App Sandbox | 直接配布初版はOFFを推奨 |
| Code Sign | Developer ID export時に正式identity |

Hardened Runtime exception entitlementは「動かないから一括で緩める」運用にしません。JIT、unsigned executable memory、disable library validation等は原則なしです。任意の`MediaCompatibilityHelper`はout-of-processの署名済みXPC／実行fileとし、任意library injectionを許しません。Appleも必要なexceptionだけを付与するよう案内しています。[Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)

### 8.5 Entitlements

非sandboxでApple framework中心なら、初版はentitlementなし、または本当に必要な最小集合から開始できます。Network updateを初版で行わなければ、起動時network entitlementの考慮も不要です。

App Sandboxを選ぶ場合は、user-selected files、security-scoped bookmark、network等を別途設計し、card erase／arbitrary helper／管理者permission修復はscope外にする必要があります。

## 9. SigningとNotarization release flow

### 9.1 推奨：Xcode Organizer

最初の正式releaseは、Xcode Organizerを使うのが最も検証しやすいです。

1. `Any Mac (Apple Silicon, Intel)`向けにArchive
2. OrganizerでArchiveを選択
3. `Distribute App`
4. `Developer ID`
5. UploadしてApple Notary Serviceへ
6. Accepted後、ticket付きexportを取得
7. signed appをDMGへpack
8. 最終DMGも署名、公証、staple

AppleはOrganizerのDeveloper ID workflowから公証へuploadできると案内しています。[Apple notarization workflow](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

### 9.2 自動化する場合

公証credentialはKeychain profileへ保存します。clear textをscriptへ書きません。Appleは`notarytool store-credentials`と`--keychain-profile`を案内しています。[Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)

一度だけ対話的に実行:

```bash
xcrun notarytool store-credentials UMIS_NOTARY \
  --apple-id "<APPLE_ID>" \
  --team-id "<TEAM_ID>"
```

app archive／export後の概念手順:

```bash
codesign --verify --deep --strict --verbose=4 "/path/to/RINKAN UMIS.app"
codesign -dvvv "/path/to/RINKAN UMIS.app"

ditto -c -k --keepParent "/path/to/RINKAN UMIS.app" "/path/to/RINKAN_UMIS.zip"
xcrun notarytool submit "/path/to/RINKAN_UMIS.zip" \
  --keychain-profile UMIS_NOTARY \
  --wait

xcrun stapler staple "/path/to/RINKAN UMIS.app"
xcrun stapler validate "/path/to/RINKAN UMIS.app"
spctl --assess --type execute --verbose=4 "/path/to/RINKAN UMIS.app"
```

stapled appからDMGを作成後:

```bash
codesign --force --timestamp \
  --sign "Developer ID Application: <組織名> (<TEAM_ID>)" \
  "/path/to/RINKAN_UMIS.dmg"

xcrun notarytool submit "/path/to/RINKAN_UMIS.dmg" \
  --keychain-profile UMIS_NOTARY \
  --wait

xcrun stapler staple "/path/to/RINKAN_UMIS.dmg"
xcrun stapler validate "/path/to/RINKAN_UMIS.dmg"
spctl --assess --type open --context context:primary-signature \
  --verbose=4 "/path/to/RINKAN_UMIS.dmg"
```

実scriptではnotary結果の`status == Accepted`をparseし、失敗時はsubmission IDからlogを取得してreleaseを停止します。`--wait`しただけでexit codeを無視しません。

### 9.3 Nested code

Xcode framework、XPC service、helper executable、最終corpusで必要と確定した`MediaCompatibilityHelper`実装等、bundle内の全codeを署名します。独立`ffprobe` binaryを前提にしません。手動signが必要なcustom helperは内側から外側へsignし、最後にapp bundleをsignします。`--deep`を署名の代用にはせず、`--deep`は最終verifyにだけ使います。

各helperで確認:

```bash
codesign -dvvv "/path/to/helper"
file "/path/to/helper"
lipo -archs "/path/to/helper"
```

期待:

- AuthorityがDeveloper ID Application
- TeamIdentifierが対象Team
- runtime flagあり

## 10. 現行Flet appを今すぐ正式署名しない理由

今回ユーザーが求める署名は、新Swift版の正式releaseへ必ず適用します。現行Flet appは次の理由で、そのままDeveloper ID署名だけを付けて配布完了とはできません。

- code signing identityとBundle IDが未設定
- Flet runtimeを利用者領域へ展開しInfo.plistを変更する
- 未署名updaterが実行programを置換する
- copy／eraseにP0の安全性問題がある
- helperとnative dependencyのHardened Runtime互換を再検証する必要がある
- GPL有効FFmpeg配布のlicense確認が必要
- current appはthin arm64で古いIntel Macを救済しない

証明書を導入した後でも、現行版を緊急配布用に署名する場合は、updater無効化、Bundle ID固定、全nested code署名、Hardened Runtime、notary、runtime test、安全性の明確な警告が別作業として必要です。新Swift版の署名計画と混同しません。

## 11. リリース判定

以下の一つでも未達なら本番releaseしません。

- assignmentがstable IDでない
- copy journalがない
- source／destination内容hash検証がない
- duplicateを未検証成功にできる
- crash resume test未実施
- source／destination抜線test未実施
- 未検証runからerase可能
- volume stable identityがない
- [安全なカード初期化要件](09_安全なカード初期化_フォルダリネーム要件.md)の`EraseEligible` predicateまたは全`ERA-AT`に未達がある。未達buildはerase機能をproduction artifactで無効化する
- `unknown／unreadable／changed`が1件でもあるrunからtokenを発行できる
- 初期化操作時のRequired Set source＋全required destination無条件再hash、token replay、same-size／same-mtime改変testが未合格
- release candidateでの専用犠牲SD／複数reader／対応OS manual destructive QAが未合格
- NAS-onlyを許可する正式policyとproduct-controlled `DestinationCapabilityProfile`が未確定なのにNAS-only runからtokenを発行できる
- UI thread sanitizer未合格
- memory budget未達
- legacy migration reportがない
- universal2または明確なCPU制約がない
- Developer ID identityで署名されていない
- Hardened Runtimeなし
- notarization Acceptedでない
- ticketがstapleされていない
- clean／offline Gatekeeper test未合格
- license／SBOM未確認
- LAN機能を含むartifactで全`LAN-AT`、pairing／mTLS、handoff crash、high-water rollback、Local Network Privacy testが未合格。未合格時はlistener／Bonjour advertise／LAN設定をrelease artifactから到達不能にする
- SD管理production adapterを含むartifactで全`SDM-AT`、contract／auth／security／Outbox crash recovery testが未合格
- 実API未確定なのにMock／fake server／staging endpointがrelease buildから到達可能、またはproduction adapterの環境／endpointを任意変更できる
