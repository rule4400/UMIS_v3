# 不具合・性能・安全性監査

## 1. 重大度の定義

| 重大度 | 定義 |
|---|---|
| P0 | 原本消失、誤コピー、誤デバイス消去、任意コード実行など。新Swift版の業務利用前に必ず解消 |
| P1 | 正常な操作で不整合、長時間停止、回復不能な部分状態、重要機能の誤表示につながる |
| P2 | 限定条件の誤動作、保守性、容量、アクセシビリティ、診断性の問題 |
| P3 | 表示、文言、dead code、文書差異等。直接のデータ事故には結び付きにくい |

## 3. P0の詳細

### R-001：仕分け後のsortでコピー対象が変わる

割当時、`scene_assignments`へ`source_files`の整数indexを保存します。[割当](legacy-source/rinkan_umis_v1.1.103.py:10876) sortは`source_files`をin-placeで並べ替えますが、割当indexを再構築しません。[sort](legacy-source/rinkan_umis_v1.1.103.py:6546) CopyWorkerは古い整数indexで現在の配列を引きます。[copy task build](legacy-source/rinkan_umis_v1.1.103.py:1754)

例:

```text
割当前: [A.jpg, B.jpg, C.jpg]
「シーン1」へ index 0 = A.jpg を割当
size順sort後: [C.jpg, B.jpg, A.jpg]
CopyWorkerが index 0 を参照 → C.jpgをシーン1へコピー
```

各素材dictの`assigned_scene`表示はA.jpgのままなので、画面件数と実コピー対象まで食い違います。

必要な修正は、`MediaAsset.ID -> Scene.ID`を唯一の正本にし、表示順はID配列のprojectionとすることです。

### R-002〜R-004：検証していないコピーを成功扱いし、消去へ進む

設定既定に`verify_checksum=True`があります。[設定](legacy-source/rinkan_umis_v1.1.103.py:1482) しかしコピーで参照されず、検証はtempとfinalの`st_size`比較だけです。[コピー・検証](legacy-source/rinkan_umis_v1.1.103.py:1947)

finalが存在すれば内容を比較せずskipし、最終成否は`fail == 0`で決まります。`skipped`は失敗ではありません。[成否](legacy-source/rinkan_umis_v1.1.103.py:1981) 成功callbackは`format_allowed=True`にします。[完了処理](legacy-source/rinkan_umis_v1.1.103.py:13172)

このため次の事故系列が成立します。

1. 保存先copyが途中失敗し、最終名の部分ファイルが残る。
2. 再実行すると、finalが存在するので無検証skip。
3. 他の失敗がなければ全体成功。
4. 警告を続行し、カードを初期化。
5. 後から保存先が不完全だったと判明しても原本はない。

Swift版では、`copied`、`durableVerifiedExisting`、`conflict`、`failed`、`cancelled`を分離し、全対象が強い内容検証と保存先耐久性の確認まで完了した場合だけrunを`durableCommitted`にします。

### R-005〜R-006：表示名で消去対象を認可する

volume候補は`/Volumes`配下を広く拾い、basenameを表示IDにします。同名は列挙順の`(2)`です。[検出](legacy-source/rinkan_umis_v1.1.103.py:13988) 初期化許可は`format_allowed`と、現在の表示文字列が`last_ingested_drive`と同じかで決めます。[ボタン状態](legacy-source/rinkan_umis_v1.1.103.py:3014)

抜去で`format_allowed`／`last_ingested_drive`を確実に失効しません。同名の別カードが同じ表示IDになれば、以前の認可を引き継ぎ得ます。確認dialogを3回出しても、表示対象と実deviceのidentityが誤っていれば防げません。

`emergency_fmt`はプロジェクト設定へ保存し、次回起動に復元されます。ONなら取り込み済みかを無視して候補volumeを初期化できます。これは永続設定にしてはいけません。

Swift版で残すなら、次に紐付く一回限りtokenが必要です。

```text
runID
source Volume UUID / Media UUID
BSD whole-disk ID
capacity
insertion generation
verified item-set hash
expiry
```

抜去、再mount、別run、内容変更、期限切れで即失効し、実行直前にDisk Arbitration情報を再照合します。監査時点では初版から外す案を最も安全と評価しましたが、その後の製品要件でアプリ内初期化を実装することが確定しました。したがって[安全なカード初期化要件](09_安全なカード初期化_フォルダリネーム要件.md)の強制gateを満たす場合だけ実装します。

### R-007：未署名updater

アプリ初期化時に毎回更新確認threadが起動し、placeholder GitHub URLへGETします。[起動](legacy-source/rinkan_umis_v1.1.103.py:2751) 現在は404を捕捉しますが、feedが有効ならJSONのURLを信頼します。

download側にはtimeout、hash、署名、size limit、content type、許可domainがありません。一時`.py`をshellで`sys.argv[0]`へ移し、`python3`で実行します。[更新実行](legacy-source/rinkan_umis_v1.1.103.py:14114)

これは有効化されると任意コード実行経路になり、PyInstaller `.app`ではMach-Oとコード署名も壊します。Swift版へ移植せず、初版は署名・公証済みDMGの手動更新とします。

## 4. copy、move、cancel、eject

### 4.1 final直書きと非トランザクション

保存先の最終名へ直接`copy2`するため、disk full、抜線、killで部分ファイルがfinalとして残ります。`.partial`、commit marker、rollback、resume journalはありません。

sourceから固定home tempへコピーし、その後保存先へコピーするため、全素材を二度読み書きします。tempは失敗・cancelでも`rmtree(ignore_errors=True)`で削除され、復旧材料になりません。[cleanup](legacy-source/rinkan_umis_v1.1.103.py:1740)

### 4.2 シーン移動

移動先衝突を確認せず`shutil.move(old,new)`します。[move](legacy-source/rinkan_umis_v1.1.103.py:5099) 同一filesystemでは既存同名を上書きし得ます。メインを先に動かし、その後`選別`コピーを動かすため、後半失敗時に両者が別シーンへ分断されます。

ファイル名変更は構造化componentから再生成せず、旧scene文字列をfilename全体で`replace`します。元filenameや撮影者名にも同じ文字列があれば、意図しない部分を変更します。

### 4.3 cancel

取り込みcancelは`is_cancelled=True`にするだけで、実行中の`shutil.copy2`は止まりません。セレクト現行実装は`current_copy_worker`ではない独自threadで、cancel flagを参照しません。UI上はcancelを要求したように見えますが、実処理は継続します。

### 4.4 eject

ejectは成功前にsource、割当、identity、format許可、drive mapをclearします。[eject start](legacy-source/rinkan_umis_v1.1.103.py:13415) `diskutil eject`が失敗すると、物理volumeがあるのにUIから消え、未保存割当も失われます。

CopyWorkerは`source_files`と`scene_assignments`の参照をそのまま持つため、eject側の`clear()`と競合します。task列挙前なら0件runが成功相当になる可能性があり、列挙後ならcopy中にunmountされ部分失敗します。

## 5. UIフリーズと並行処理

### 5.1 同期I/O

保存先TextFieldは文字変更ごとに同期保存へ到達します。[入力](legacy-source/rinkan_umis_v1.1.103.py:2633) 保存は既存JSONのbackupを最大5秒待ち、main JSONを書き換えます。[save](legacy-source/rinkan_umis_v1.1.103.py:1546)

文書には過去の設定backup copyが9.4秒、71.4秒停止した記録があります。[CLAUDE.md](legacy-source/CLAUDE.md:278)

`_copy2_bounded()`はcopy例外を戻り値へ反映せず、timeout後もdaemon threadを停止しません。古いbackup threadが後から完了し、新しい保存と競合し得ます。

### 5.2 UI ownership

初期化時に3、2、2 workerの3つのThreadPoolExecutorを作ります。[executors](legacy-source/rinkan_umis_v1.1.103.py:2462) これにdrive monitor、freeze watchdog、scan、scrub prefetch、load test、copy、eject、update、Timer等が加わります。

CopyWorker、Select copy、scan、drive monitor、update thread等からFlet controlを直接変更します。これを抑えるためFlet private lockと`Page.update`をmonkey patchしています。[instrumentation](legacy-source/rinkan_umis_v1.1.103.py:332) 直列化補助はあっても、UI状態を1つのthreadが所有する設計ではありません。

Swift版はUIを`@MainActor`へ閉じ、workerはimmutable progress eventを`AsyncStream`で返す構造にします。

## 6. スキャンとメディア性能

### 6.1 二重走査

800件以下でもtop folderを再帰countしてから、同じtreeを本スキャンします。pre-scan再帰にcancel checkがなく、mediaを切り替えてもI/Oが終了まで続きます。

### 6.2 controlとthumbnailの作り過ぎ

段階表示上限はあるものの、素材ごとにgrid cardとlist rowを両方構築して保持します。セレクトgridは全cardを`Row(wrap=True)`へ載せ、cell reuse／virtualizationではありません。表示外素材を含む`source_files`全体をthumbnail生成対象にします。

### 6.3 文書上の既知性能

既存文書の320件基準では、scan約0.005秒、thumb生成約12.6秒、RSS増分270〜285MBが生成後も維持、540p proxy約3.7秒です。[CLAUDE性能記録](legacy-source/CLAUDE.md:297) 300件超のモード切替2〜3秒、Flet親子関係不整合も既知です。[HANDOVER](legacy-source/HANDOVER.md:161)

この基準は短いsynthetic素材と高速ローカル環境で、実尺4K／実SD／NAS試験ではありません。

### 6.4 今回の実測

隔離した実アプリで、30本の短い640×480動画と200枚のJPEG、計230件の内蔵負荷試験を実行しました。

| 項目 | 結果 |
|---|---|
| 完了時間 | 約11.0秒 |
| フリーズ判定 | なし |
| PERF warning | 0 |
| 処理中の合計RSS | 約447MiB |
| 処理後の合計RSS | 約410MiB |
| Python本体 | 約137MiB |
| Flet View | 約244MiB |
| bootloader等 | 約30MiB超 |
| 開発者パネル表示 | 約86〜106MiB程度 |

開発者パネルはFlet View等を含めず、総RSSを大幅に過小評価します。負荷試験は成功しても、400MiB超が残ること自体が、古いMac／低メモリ環境の訴えを説明します。

## 7. cache監査

### 7.1 quota

proxy 10GiB、scrub 2GiBには上限がありますが、thumbnail、1080 preview、duration、freeze dump、faulthandlerには統一上限がありません。「すべて削除」はproxy、scrub、duration、legacy、過去の保存先cacheを残します。

### 7.2 fingerprint

cache keyはpath＋size＋mtime_nsで、内容hashではありません。同size／mtimeを保持した差替えで古いcacheを使います。NASのmtime粒度やUnicode NFC／NFD差でも不安定です。

### 7.3 Quick Look race

同じ共有cache dirへbasename由来の出力を生成しglobで回収するため、異なるfolderの同名素材を並行処理すると、出力を拾い違えたり削除し合う余地があります。

## 8. 設定、履歴、ログ

### 8.1 設定

- schema versionなし
- top-level中心の浅いmerge
- 型／必須key／値域検証なし
- writer lockなし
- temp名がPIDだけで同一processの並行saveが競合
- fsyncなし
- `.bak`だけ存在する場合の回復が不十分
- 手動保存の戻り値を無視して成功表示する経路あり
- 設定Cancelが即時保存済み変更をrollbackしない

### 8.2 履歴

成功runだけを中心に記録し、partial failure、cancel、個別file status、duplicate判断、hashを持ちません。JSON破損月は無音skipです。clearはtrash／backupなしのunlinkです。履歴filter／clearの一部UIは未接続です。

### 8.3 ログ

通常logはrotateしますが、起動ごとのfaulthandlerとfreeze dumpにretentionがありません。full path、username、撮影者、カードID、permission情報を含み得ます。

### 9.1 現行署名

| App size | 124MB |
| Bundle Identifier | `RINKAN UMIS` |
| Signature | ad-hoc |

specは`codesign_identity=None`、`entitlements_file=None`、`bundle_identifier=None`です。[spec](legacy-source/RINKAN%20UMIS.spec:59) 配布launcherはquarantineを再帰削除します。[launcher](legacy-source/distribution/初回起動.command:36)

ad-hoc signatureの整合性確認は配布者のidentityを保証しません。新Swift版ではDeveloper IDと公証をrelease gateにします。

### 9.2 permission修復

管理者権限で選択root全体へ再帰`chgrp`／`chmod`します。UMIS以外の既存file、NAS ACL、共有group方針を変える可能性があります。Swift版は自分が作成するfileだけの権限を制御し、既存tree全体を変更しません。

### 9.3 FFmpeg license

同梱FFmpeg 8.1.2はconfigureに`--enable-gpl --enable-version3`があり、libx264／libx265等も含みます。FFmpeg公式資料によれば、`--enable-gpl`を有効にしたbuildはGPL扱いになります。[FFmpeg License](https://ffmpeg.org/doxygen/trunk/md_LICENSE.html) vendorには実行バイナリとREADMEはありますが、対応source、build recipe、license一式、配布ページの案内を確認できませんでした。

これは法的断定ではなく、配布前にライセンス遵守を確認すべきリスクです。Swift版ではApple frameworkで置換できる範囲を最大化し、helperを残す場合はbinary hash、source、configure line、license、SBOM、配布義務を固定します。FFmpeg自身も、どのoptional libraryを有効にするかでLGPL／GPLが変わると説明しています。[FFmpeg legal](https://ffmpeg.org/legal.html)

## 10. UXとアクセシビリティ

### 10.1 実動作で確認した不一致

- Aboutの更新履歴は「履歴ファイルが見つかりません」。specにCHANGELOGがないためです。
- Helpは「選別を実行」と案内しますが、実ボタンは「N件をセレクトに追加」です。
- Help記載のfile Drag & Drop importはありません。
- 初回walkthroughは自動表示されません。
- Settings Cancelは保存済み変更を戻しません。
- Select copy中のCancelは対象threadへ届きません。
- 会場名を付けるrename previewと実copy filenameが一致しません。
- category／scene／photographer folder、checksum、folder order等、設定しても働かない項目があります。
- Select copyは既存skipも「追加件数」に数えます。
- Select moveは「その他」へ移せず、衝突確認もありません。

### 10.2 Accessibility

Computer Useで取得したAccessibility treeでは、Settings内の多数の操作行がbuttonではなくtextとして見え、TextField valueも空として見えるものがありました。VoiceOver、Full Keyboard Access、automationから操作対象を正しく認識しにくい状態です。

Swift版では、すべてのinteractive controlへrole、label、value、hint、keyboard focus、minimum hit targetを付け、VoiceOverだけで取り込み計画の確認まで完了できることを受入条件にします。

## 11. 保守性

AST監査では`except` handler 442個、passだけのhandler 297個、裸の`except:` 130個でした。履歴破損、UI update失敗、cache削除失敗、stat失敗等が無音になり、部分状態を成功表示する要因になります。

本番ソース内に診断、load test、selftestが入り、旧`SelectWorker`、旧`build_ui()`、legacy cache、dead drag state等が共存します。自動test suite／CIはありません。PyInstaller warningは269行、missing module記録251件ですが、既知optionalと新規問題を分けるallowlistもありません。

## 12. 現行アプリを参照実装として使う際の制約

- 本番カードを初期化しない。
- sort後の仕分け結果を信用せず、出力を別手段で照合する。
- 既存同名が一件でもあるrunを成功と見なさない。
- sourceとdestinationの別バックアップを保持する。
- 自動更新feedを有効化しない。
